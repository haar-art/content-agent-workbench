# 内容 Agent 工作台 v2

一个从零手写的「内容生产 Agent」：**输入主题 → 输出可直接拍摄的短视频脚本包**（标题钩子 / 口播正文 / 配图提示词 / 话题标签）。

**不依赖 LangChain** —— 工具调用、上下文组装、可观测性、评测全部手写，目的是把 Agent / RAG 的底层机制真正跑通一遍。

## 工程闭环

```
能读 → 能自己决定 → 能执行 → 能留档 → 能自检（数量 + 质量）
```

## 目录

| 文件 | 作用 |
|---|---|
| `context_builder.py` | 4 层上下文组装器（系统 / 用户 / 长期记忆 / 任务）+ `ContextSession` 共享容器 |
| `agent_content_v2.py` | 5 步流水线（人设 → 选题 → 文稿 → 配图 → 组装） |
| `read_candidates.py` | 读选题池 → `list[dict]`（文本解析） |
| `tools.py` | 工具说明书（JSON schema，给模型看） |
| `agent_loop.py` | Function Calling 循环 + 步数护栏 + 计时 + 异源自检 + 落档 |
| `eval_runs.py` | 数量评测：读运行档案 → 判漏项 → 汇总通过率 |
| `eval_quality.py` | 质量评测：规则型判据（标题字数 / 门槛术语），直读素材不绕模型 |
| `AGENTS.md` / `USER.md` / `MEMORY.md` | 三层上下文的文件化版本（系统 / 用户 / 长期记忆） |

> **不在本仓库的文件**（都是运行数据，不是代码）：
> `.env`（密钥）、`runs.jsonl`（运行档案，含个人选题）、`output/`（真实脚本产出）、`candidates.md`（个人选题池）。

## 技术要点

- **原生 OpenAI SDK 手写**，不依赖 LangChain —— 为理解 Agent / RAG 的底层机制
- **Function Calling 循环**：工具说明书 + 真实函数 + 函数表按 `name` 绑定
- **可观测性**：每次运行自动落一行结构化档案（JSONL 追加，不覆盖历史）
- **评测分两层**：数量（漏项检测）+ 质量（规则型判据）
- **评测器做过「验谎测试」**：手动伪造一条失败记录，确认它真能抓到
- **上下文工程**：4 层上下文 + 共享 `messages` 容器（治多步漂移）

## 一个值得讲的工程故事

一开始想直接复用一套现成的 rubric 给选题打分。把它跑起来、**把 25 条的分数摊开一看** ——

> **全挤在 3.4 ~ 4.7 之间**（一个 0–10 的量表，只用了 **13%** 的跨度），**区分度接近零**。

排查之后才明白：**打分的不是程序，是模型；而模型打分会「趋中」** —— 它习惯性全往中间塞，不敢给极端分，所以谁和谁都分不开。

**这条路走不通，于是换成自己设计规则型判据**（标题字数 / 门槛术语）。

这个故事的价值不在于「我做了个评测」，而在于 **「我用数据推翻了自己的方案」**。

## 运行

1. 建 `.env`（本仓库不含密钥）：

   ```
   OPENAI_API_KEY=你的key
   OPENAI_BASE_URL=https://api.deepseek.com
   OPENAI_MODEL=deepseek-chat
   CANDIDATES_PATH=你的选题池md路径
   ```

2. 依次跑：

   ```bash
   python agent_loop.py     # 跑一次循环，落一行运行档案
   python eval_runs.py      # 数量评测（漏项检测）
   python eval_quality.py   # 质量评测（规则型判据）
   ```

## 已知限制

- `agent_loop.py` 目前只接了一个**只读**工具（`read_candidates`）—— **「写」能力还在计划中**
- `eval_quality.py` 是规则型判据，**测不到「信息不完整」**（比如标题默认读者已经知道某个产品名）
- 判据阈值（如标题 ≤ 20 字）是**待校准的 v0** —— 需要真实播放数据回来修正
